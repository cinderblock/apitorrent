# Torrent list: never look empty while loading, stream the snapshot in

## Goal

Coming back to the torrent list (from Settings, after an import) showed "No torrents here
yet" with the Add and Import buttons while the daemon had thousands of torrents. The list
should say it's loading, and the torrents should appear as they arrive rather than all at
once after one big message. Thousands of torrents must stay smooth.

## Environment / context

- Web: `web/src/api/sync.ts` (`SyncClient`), `web/src/state/torrents.ts` (`applySync`),
  `web/src/App.tsx` (the `empty` message), `components/TorrentTable.tsx` and
  `TorrentCards.tsx` (already virtualized with `@tanstack/react-virtual`).
- Server: `crates/apitorrent-server/src/sync.rs`; message types in
  `crates/apitorrent-types/src/lib.rs` (`SyncMessage`, TS generated by `ts-rs`).
- Desktop: the page's socket goes through `commands::sync_open` →
  `Backend::sync` → `Remote::sync` (`crates/apitorrent-client/src/remote.rs`) or the
  in-process server. `notify.rs` opens its own socket for finish notifications.

## Findings

- Cause: `App` stops the sync socket when it unmounts (any page change). On return the
  old state stays, with status still `live`, so a list that was empty before an import
  looks empty until the new snapshot arrives: about 6 MiB of JSON for 10,000 torrents,
  uncompressed through the desktop app.
- The lists are virtualized already; the cost is the single snapshot message.
- ts-rs only rewrote `web/src/api/generated/SyncMessage.ts` when its own test ran by
  name (`cargo test -p apitorrent-types --lib export_bindings_syncmessage`); a broader
  filtered run left it stale once.

## Decisions

- Chunked snapshots are opt-in (`?chunks=1`), so older clients (an older desktop app
  against a newer daemon) get one snapshot as before, and a newer client against an older
  daemon simply gets no `total`.
- Protocol: `snapshot` gains an optional `total`; when it's larger than the torrents in
  that message, `snapshotPart` messages follow until `total` have arrived. Patches come
  only after the last part. Parts go newest-added first (the list's default sort): 100,
  then 1,000 each.
- During a resync (the client already has torrents), the old list stays up and the new
  parts are laid over it; the exact new set replaces it when the last part lands, so rows
  don't vanish and reappear.
- The sync socket lingers for 2 minutes after leaving the list, so a trip to Settings
  comes back to live data at once. A real restart reports `connecting`.
